# 50-Category Real-World Agent Blueprint Registry

> **Status:** Completed 50-category registry and review ledger  
> **Baseline:** 2026-08-31  
> **Target:** 50 distinct workload blueprints, each developed from zero-to-production and refined through the full review program  
> **Program contract:** [Real-world agent blueprint expansion program](agent-blueprint-expansion-program.md)

This registry turns the repository's blueprint ambition into an inspectable scope. The target is exactly 50 useful workload categories, not 50 renamed chatbots. Every category must retain a materially different tool environment, authority model, state or recovery contract, evaluation environment, or deployment shape from its nearest neighbor.

## Completion state

All fifty categories, their owned folders, and their research packets are integrated in this repository. The review labels below describe documentation maturity, not live background work: this baseline is closed, and any future refinement must be a separately scoped, evidence-backed review rather than an assumption that a worker is still running.

The names are stable planning handles, not permission to create shallow folders. A specialist must still pass the category promotion scorecard before its blueprint is promoted. If research proves that a row duplicates another category, the coordinator records the merge and replaces the vacated slot with a genuinely distinct category; the repository does not preserve duplication merely to keep a number.

## Mandatory zero-to-production path

Every one of the 50 blueprints must let a reader progress through the same capability journey while receiving workload-specific answers:

| Stage | Reader outcome |
|---|---|
| 0 — qualify the problem | Decide whether the workload needs an agent at all; document the deterministic, workflow, retrieval, or ordinary-software baseline |
| 1 — first bounded loop | Build the smallest model-directed loop with typed tools, explicit completion, hard budgets, and no unnecessary external authority |
| 2 — useful MVP | Add the real workload environment, evidence-bearing results, context assembly, short-term working state, approvals, and representative evaluation tasks |
| 3 — reliable v1 | Add durable task state where needed, compaction, long-term memory only where justified, idempotency, reconciliation, cancellation, recovery, and third-party integration contracts |
| 4 — production readiness | Add identity, tenancy, least privilege, threat controls, release gates, observability, tracing, SLOs, runbooks, deployment, rollback, and incident response |
| 5 — scale and resilience | Add admission control, queues, workers, isolation, capacity models, disaster recovery, cost controls, regional or tenant boundaries, and safe degradation |
| 6 — continuous evolution | Add offline and online evaluation loops, failure mining, model/tool/schema upgrade gates, feedback governance, drift detection, refresh triggers, and deprecation plans |

Memory is never added as a feature checkbox. Each blueprint must decide separately whether it needs ephemeral turn context, run-scoped working memory, durable task state, user or account memory, domain knowledge, or episodic outcome memory; then define provenance, retrieval, poisoning, retention, deletion, and evaluation controls. The same rule applies to context compaction, third-party connectors, multi-agent delegation, and durable execution: include them only when the workload justifies them, but explain the decision explicitly.

## Registry invariants

Before launching or promoting a category, compare it with the named neighbor and record at least three materially different seams across tools/environment, authority, task state, failure recovery, evaluation, and deployment. A specialist may recommend a better name or scope, but must not silently broaden into a neighboring row.

High-stakes categories are engineering blueprints, not permission to automate protected professional judgment. Legal conclusions, financial filings, employment decisions, insurance adjudication, suspicious-activity filings, clinical decisions, participant safety decisions, critical-infrastructure control, and similar consequences retain qualified human or deterministic policy ownership unless authoritative evidence and law explicitly support a narrower automation boundary.

The coordinator keeps task status here synchronized with the rolling pool. `Active Pass 1` means research and construction are in progress; `Pass 2 active` means a reviewed first pass is undergoing dedicated usefulness refinement. Neither means the output has passed production/security, contradiction, or final integration review.
